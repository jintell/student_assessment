# TASK-PLAT4-OBS-001 — Alert Proposals for FEAT-OPS-004

Status: **PUBLISHED FOR FEAT-OPS-004 INTAKE**, 2026-10-16. Architecture §16.4 defines the backlog alert only; the four proposals below are gaps requiring Ops/architecture review, not additions claimed to exist in the baseline. Repository publication is the handover event; receipt, routing approval and deployment remain pending. No external notification was sent.

| Proposal | Trigger and severity | Signal / prerequisite | Recovery and runbook |
|---|---|---|---|
| Outbox failed event | Any current FAILED row, P2 | Fresh `max(outbox_backlog_depth{state="FAILED"}) >= 1`, scoped to deployment. The failed-transition counter alone cannot prove no unresolved rows remain. | Investigate until eligible audited redrive or approved disposition leaves no unresolved row; [failed rows](../../runbooks/outbox-failed-rows.md). |
| Relay tick liveness gap | No completed relay tick for more than 60 seconds while relay is expected enabled, P2 | `outbox_relay_tick_total` increase is a tick-attempt signal, including losing contenders. Ops must combine fresh target availability and enabled-state inventory; reset/missing series must not be treated as healthy. Successful lock-owner work remains a separate check using sweep success/publication. | Restore expected ticks and verify backlog progress; [stalled relay](../../runbooks/outbox-relay-stalled.md). |
| Integration DLQ nonempty | `integration.dlq` depth at least one, P2 | Fresh `rabbitmq_queue_depth{queue="integration.dlq"}` from the approved broker exporter, with environment/vhost identity and bounded labels. Verify whether source reports ready plus unacknowledged; both must be visible. | Classify and resolve without bulk acknowledgement; [DLQ](../../runbooks/integration-dlq.md). |
| Unhandled event version | At least one unhandled-version dead letter, P2, distinct from poison | Broker/dead-letter owner must supply a bounded-reason count or depth derived from `UNHANDLED_EVENT_VERSION`. The application currently carries this distinct reason through `DeadLetterPublisher`/`DeadLetterAlertSink`; no dedicated registered Prometheus metric or deployed sink is claimed. | Deploy a compatible consumer and validate its version declaration before controlled replay; [DLQ](../../runbooks/integration-dlq.md). |

Do not add tenant/event IDs, raw event types or exception text as labels. Scope aggregation to one deployment; global snapshots use max, local event counters use rates/sums. Ops must decide evaluation intervals, notification grouping, inhibition, routing and missing-data/freshness treatment, and retain positive/negative/recovery tests. Do not auto-resolve the unhandled-version condition merely because a message moved queues.

The existing P2 backlog rule is in `config/alerting/outbox-backlog.rules.yml`; it is not one of these four proposals. These proposals remain uninstalled pending acceptance. Consumer version capability, missing relay assembly and broker/staging provisioning are tracked by the owning features and outbox P8.5/P8.6.
