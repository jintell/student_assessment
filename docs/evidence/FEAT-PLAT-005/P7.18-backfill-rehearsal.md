## Interruption And Resumption

`BackfillRehearsalIntegrationTest` ran the production
`ResumableBackfillHarness` through a transactional PostgreSQL checkpoint
adapter. The first worker run stopped after ten committed batches:

| Observation | Result |
|---|---:|
| Rows processed before interruption | 2,500 |
| Persisted exclusive cursor | 2,500 |
| Rows processed after restart | 10,000 total |
| Final exclusive cursor | 10,000 |
| Incorrect or missing target values | 0 |
| Rows updated more or less than once | 0 |

The resumed run used a newly constructed harness and repository instance. It
therefore recovered from the database checkpoint rather than retaining an
in-memory cursor.

## Concurrent Write Latency

A concurrent PostgreSQL upsert probe represented the answer-acceptance write
shape for the duration of both worker runs.

| Measurement | Result |
|---|---:|
| Samples | 434 |
| p95 | 2.426083 ms |
| `NFR-PERF-001` answer-acceptance limit | 1,000 ms |
| Rehearsal elapsed time | 3,155 ms |
| Verdict | PASS |

This rehearsal proves that the throttled foundation backfill does not breach
the numeric answer-acceptance p95 bound on the current production-shaped
fixture. It does not replace the normative 30-minute application load test at
the full Phase 1 workload profile; that release gate remains owned by
`FEAT-OPS-005` after the delivery tables and answer endpoint exist.
