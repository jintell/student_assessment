## Walkthrough Performed

### 1. Grant matrix

Reviewed `docs/grant-matrix.md` and the executable source at
`src/main/resources/db/grants/grant-matrix.json`.

- Each `app_<module>` role is `NOLOGIN`, owns only its module access, and has
  append-only access to the shared audit and outbox contracts.
- Pool login roles have no direct object grants. They can act only after a
  transaction assumes an allowed module or composite role.
- `app_txn_examentry` has an explicit minimum grant list and is narrower than
  the union of the module roles it replaces.
- Generated SQL and the live grant-diff gate derive from the same matrix, so
  an extra or missing privilege fails verification.

### 2. R9 installation protocol

Reviewed `docs/conformance-rules.md` and `SecurityContextInitializer`.
For a tenant transaction, the first two statements are, in order:

```sql
SET LOCAL ROLE <permitted_role>;
SET LOCAL app.tenant_id = '<tenant_uuid>';
```

No application statement may run first. The decorator refuses an incomplete
context with `R9_CONTEXT_NOT_FIRST`, while the grantless login role provides an
independent database backstop. Role selection is closed and cannot be supplied
as arbitrary runtime input.

### 3. Reset-on-release hazard

A pooled physical connection outlives a request. Returning it with stale role
or tenant state could expose the next borrower to another request's authority.
Every completion, error, cancellation, read-timeout, and statement-timeout path
therefore rolls back when needed and performs:

```sql
RESET ROLE;
RESET ALL;
```

Cleanup completes before the connection is returned. A reset failure is
propagated and increments `db_connection_reset_failure_total`; it is never
treated as harmless cleanup noise. The adversarial suite forces physical
connection reuse, including saturated small-pool reuse, across tenants and
roles.

### 4. Authoring a tenant-scoped table

Reviewed `docs/tenant-scoped-tables.md` and the reusable RLS template.

1. Create the table in its owning module schema with
   `tenant_id uuid NOT NULL`.
2. Enable and force RLS in the same versioned module migration.
3. Add the single `tenant_isolation` policy using strict
   `current_setting('app.tenant_id', false)::uuid` in both `USING` and
   `WITH CHECK`.
4. Keep tenant predicates in slice queries; RLS remains the independent
   backstop.
5. Use identifiers for cross-module references and never create a
   cross-schema foreign key.
6. Run the real-PostgreSQL catalogue and tenant-isolation gates.

The catalogue discovers tenant scope from the `tenant_id` column and rejects
missing, unforced, weakened, duplicated, or widening policies.
