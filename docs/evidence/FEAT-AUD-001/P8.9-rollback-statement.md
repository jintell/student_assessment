# P8.9 audit rollback statement

Published 2026-10-17. This states the rollback policy; it does not authorize a
particular deployment or claim that the current release passed its N-1 drill.

## Code-only rollback after EXPAND

Audit-feature migrations V3–V14 declare `cbt:phase EXPAND`; the earlier V1/V2
schema/grant bootstrap files have no phase header. Apply reviewed forward
migrations before dependent code. Keep the resulting N schema when
rolling back application code: the retained immutable N-1 image is eligible
only when matching compatibility evidence proves N-1 runs against N's schema,
grants and stored data. Do not remove new tables/columns, reverse grants,
delete audit history, clear Flyway checksums or edit an applied migration.

`RollbackPolicy` requires the immutable previous-image digest and green
evidence for the same release/manifest checksum/digest. Missing, failed or
unavailable evidence denies rollback. Before rollout, retain the image,
manifest, migration classification, checksums and compatibility result; after
code rollback verify health and the audit chain without rewriting evidence.
Continue to propagate audit-append failure to the business transaction.

The current [P7.27 pipeline record](P7.27-clean-pipeline-run.md) is blocked on
the intended `CBT_PREVIOUS_IMAGE_DIGEST`; it is not N-1 compatibility proof.
The published policy is complete, while current-release rollback eligibility
remains conditional on supplying and verifying that release input.

## CONTRACT changes

A CONTRACT-phase audit migration/release is never rolled back. Keep the schema,
halt the rollout, record the incident and ship a reviewed forward fix.
`RollbackPolicy` refuses CONTRACT even when compatibility evidence is green.
Do not use restore as a disguised schema undo that loses newly accepted audit
evidence; disaster recovery follows the separate recovery/verification plan.

## Historical codec compatibility

`hash_algo_version` distinguishes persisted hash/codec semantics. The current
`CanonicalJsonCodec` writes version 1 and its golden vectors freeze canonical
bytes. A codec change must introduce a new explicit version and a forward
deployment that can verify every retained old version, preserving its codec,
public keys, signatures, roots and checkpoints. Never re-hash/re-sign old rows
or reinterpret version 1 using new serialization rules.

The version column enables versioned roll-forward; it is not an implemented
multi-version decoder or automatic downgrade guarantee. The current emitter
rejects a head whose hash version differs from its supported codec. Before new
versions are written, prove every potential rollback reader/verifier can read
them; otherwise that old binary is not a valid rollback target. Roll forward
with reviewed version support and defined epoch transition instead of altering
history to make old code work.

Validation: `RollbackPolicyTest` and `CanonicalJsonGoldenVectorTest` pass.
Those local tests verify policy/byte invariants, not release-image availability
or a current N-1-against-N deployment rehearsal.
