# P9.4 Sweep-Staleness Alert Proposals

Date: 2026-10-16

Status: proposed to `FEAT-OPS-004`; no alert rule is claimed implemented.

## Proposed Rules

| Rule | Severity | Condition |
|---|---|---|
| `SweepStale` | P2 | For an enabled sweep, `time() - sweep_last_success_timestamp_seconds` exceeds three configured intervals. |
| `AutoSubmitSweepStale` | P1 | For enabled `auto-submit`, the same three-interval condition holds. |

The alert generator must read each enabled row's interval from
`platform.sweep_registry`; it must not apply one hard-coded duration to all
sweeps. Newly enabled sweeps receive a three-interval startup allowance before
their zero last-success timestamp can page. Disabled rows do not alert.

The P1 exception exists because a missed auto-submit sweep violates
`REQ-ASMT-021`, not merely an operational freshness preference. Route both
rules with the `sweep` and `runtime_role=worker` dimensions and link the stalled
sweep runbook.

Architecture section 16.4 already defines an auto-submit backlog alert. That
alert remains a useful volume proxy, but it cannot distinguish a healthy busy
sweep from a scheduler that has stopped ticking. These proposals add the
missing execution-freshness signal and do not rewrite section 16.4 locally.
