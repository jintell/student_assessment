# PIN-Retrieval KEK Policy Precondition

Feature: `FEAT-PLAT-006`

Task: `P6.2`

Owner receiving this precondition: `FEAT-EXAM-002`

## Required Policy

The PIN-retrieval key-encryption key must be a dedicated, non-exportable key.
Its provider policy must resolve workload identities to immutable provider
principal identifiers and enforce all of the following:

| Principal | `Encrypt` | `Decrypt` | Required decision |
|---|---:|---:|---|
| `cbt-pindist` distribution identity | Allow | Allow | The only workload principal granted either operation |
| `cbt-api` request identity | Deny | Deny | Explicit deny |
| `cbt-platform-worker` background identity | Deny | Deny | Explicit deny |

The allow must name the exact provider principal federated from
`system:serviceaccount:<namespace>:cbt-pindist`. It must not use an account,
project, namespace, cluster or wildcard principal. API and worker must remain
explicitly denied even if a broader inherited policy would otherwise allow
key operations. The three principal identifiers must be distinct and must come
from the fulfilled P6.1 Platform Ops record; this document does not invent or
substitute identifiers while provisioning is pending.

The policy must also deny workloads the ability to export key material,
delegate access, mutate the policy, disable the key or schedule deletion. Key
administration, where required by the provider, must use a separate Security
administrator identity that receives no `Encrypt` or `Decrypt` permission.

## Ownership and Evidence Boundary

`FEAT-EXAM-002` owns creation and application of the retrieval KEK policy,
including provider-specific condition keys and operations. It also owns the
staging attestation `ARC-VERIFY-025`: `Decrypt` must be denied when attempted
with real `cbt-api` and `cbt-platform-worker` credentials and permitted with
the real `cbt-pindist` credential. That attestation, plus Security and Platform
Ops approval, is the evidence required to discharge architecture condition A4
and `REQ-SEC-014`.

This precondition records the required policy shape only. It does not create a
key, grant access, attest a denial, discharge A4, or claim that P6.1 federation
has been fulfilled. Mocks, source inspection and application-level rejection
are not substitutes for the provider-backed staging verification.

## Acceptance

The handoff is complete when `FEAT-EXAM-002` treats this exact allow/deny matrix
as an input to its implementation and retains immutable provider evidence for
the three authorization attempts. Evidence must identify the policy version,
key alias or non-secret resource identifier, workload principal, operation,
decision and timestamp without retaining credentials, tokens, plaintext PINs,
ciphertext or wrapped data keys.
