# P9.3 Runtime-Role Telemetry Registration

Date: 2026-10-16

Status: registered against the `FEAT-OBS-001` role-parity contract adopted at
runtime task P1.9.

## Identity Contract

| Signal | Registration | Closed values |
|---|---|---|
| Micrometer metrics | common label `runtime_role` | `api`, `worker`, `pindist` |
| OTLP logs, metrics, and spans | resource attribute `service.runtime.role` | `api`, `worker`, `pindist` |
| Structured logs | field `role` | `API`, `WORKER`, `PINDIST` |

`RuntimeTelemetryConfiguration` applies the metric label centrally and rejects
disagreement between the active profile and `CBT_OBSERVABILITY_ROLE`.
`OpenTelemetryTracerConfiguration` builds the common resource used by all
three SDK providers. Database-role labels remain separate and are not
overwritten.

## Saturation Views

The common role dimension partitions existing saturation signals without
creating role-specific telemetry configuration:

- `api`: HTTP route-class latency/load and the general/exam-path database pool;
- `worker`: grading queue/consumer utilisation and worker/lock pool pressure;
- `pindist`: reserved-route HTTP load and PIN-distribution pool pressure.

Deployment scaling continues to use the approved per-role signals in
`deploy/runtime/values.yaml`: CPU plus exam-path p95 for `api`, grading queue
depth for `worker`, and no HPA for the fixed two-replica `pindist` workload.
The telemetry dimension distinguishes those workloads; it does not alter HPA
ownership or thresholds.

## Verification

`RuntimeTelemetryConfigurationTest` exercises every `RuntimeRole`, proves the
common metric label and OTLP resource attribute, preserves a database `role`
label, and rejects configuration disagreement. Role-log tests independently
cover the uppercase structured-log field.
