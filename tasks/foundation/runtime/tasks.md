**Objective.** Run one artifact in three profile-selected roles — request serving, background work and the
isolated PIN-distribution route — with different enabled beans and identical code, migrations and
configuration surface; guarantee that a scheduled sweep runs on exactly one replica per tick; and sequence
shutdown so in-flight work completes or remains recoverable.

**Why this feature's timing matters.** Plan §10 lists "three roles deploying from one image with scheduler
singletons proven" as a **Phase 0 exit criterion**, not merely a feature DoD, and four sibling task lists
already defer work to it: `FEAT-PLAT-004 tasks.md` `TASK-PLAT4-DEFECT-004` (the relay ships its own advisory-lock
acquisition and adopts this registry at its `P7.17`), `FEAT-PLAT-005 tasks.md` assumption 4 (graceful shutdown
sequencing), `FEAT-PLAT-003 tasks.md` (the kernel must add no per-role configuration surface) and `FEAT-OBS-001 tasks.md`
(telemetry must be role-parity identical across the three roles). Nine later features hard-depend on it.
It is also the feature that mitigates `T-01`, the programme's accepted one-deployable trade-off, which
`FEAT-PLAT-001 tasks.md` explicitly forwards here.

### Confirmed implementation decisions

| Decision                       | Choice                                                                                                                                                                                                                                                                                                    | Consequence                                                                                                                                                                                                                             |
|--------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Layer placement                | `RuntimeRole`, `@RoleScoped`, `SweepDefinition`, `SweepLock` in `platform.api`; every adapter and the runner in `platform.infra`; the registry migration in the `platform` module                                                                                                                          | §5.1 puts schedulers in each module's `infra/` but permits no shared service layer, and never says where a cross-cutting lock primitive lives. `platform.api` is the only placement that lets a `delivery` sweep declare a role under R2 |
| Lock primitive                 | `pg_try_advisory_lock` keyed by sweep name, held for the whole tick, released in a `finally` — §8.2 verbatim. Losers skip the tick and record the outcome                                                                                                                                                  | Try-semantics, not blocking. A loser that waited would convoy every replica onto one sweep and defeat the bulkhead the roles exist for                                                                                                   |
| Second adapter shipped now     | A `pg_try_advisory_xact_lock` adapter behind the same port, built and tested in parallel                                                                                                                                                                                                                  | §15.2 pre-authorises a PgBouncer escalation (`T-15`) and states that session-level locks do not survive transaction pooling. Shipping both makes that a configuration change rather than a redesign                                      |
| One port, not two mechanisms   | `SweepLock` is the only advisory-lock acquisition in the codebase; `FEAT-PLAT-004`'s local acquisition is retired against it                                                                                                                                                                              | Closes `TASK-PLAT4-DEFECT-004`. ### Assumptions

1. **The pool login roles `app_api`, `app_worker` and `app_pindist` and the `platform` schema already
   exist**, delivered by `FEAT-PLAT-002 tasks.md` `P3.11`, `P3.7` and `P3.9`, together with the per-workload pool
   figures of `P1.6` and `P4.14` — `cbt-api` 14 with 8 reserved for exam-path routes, `cbt-worker` 10,
   `cbt-pindist` 5. This feature consumes those figures and defines none.
2. **No new database role is required.** `pg_try_advisory_lock` needs no object grant, so unlike
   `FEAT-PLAT-004 tasks.md` this feature adds no narrow role — only a `SELECT` grant on `platform.sweep_registry`
   to the background workload. Recorded so the absence reads as analysis, not oversight.
3. **`ActorContext` and its system-actor enumeration are `FEAT-PLAT-003`'s types** (`FEAT-PLAT-003 tasks.md`
   `P4.2`) and are consumed, not redefined. The controlled `Clock` is likewise consumed — a sweep computes
   no `Instant.now()`.
4. **This feature ships no sweep body and no business route.** What ships is the role mechanism, the lock
   port and its two adapters, the registry, the startup validators, the shutdown sequencing, the in-process
   bulkheads, two conformance rules and one test-only reference sweep.
5. **Kubernetes manifests are authored by Platform Ops** (`FEAT-OPS-007`); this feature supplies the
   per-role values they must carry — profile, pools, replicas, HPA bounds, `ServiceAccount`, `NetworkPolicy`,
   `preStop`, `terminationGracePeriodSeconds` and session affinity off — and asserts them where assertable.
6. **`cbt-migrate` is not a fourth role.** The `--migrate-only` entrypoint is `FEAT-PLAT-005`'s; the bean
   matrix here is not to be read as the complete set of process modes (`TASK-PLAT6-OBS-004`).
7. **Staging does not exist yet** (plan §3.2). Every obligation whose gate is Staging is delivered as far as
   Phase 0 allows and explicitly scheduled, not claimed.
